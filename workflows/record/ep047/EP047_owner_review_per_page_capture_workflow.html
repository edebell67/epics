Owner review — per-page capture

Design B: the owner reviews each screen while looking at it, answers accumulate in the browser as they browse, and owner-preview.html is retained as the single consolidation and submit point. Any screen never reviewed resolves to No Action. Replaces the centralised card-stack design previously specified in the ep044 owner review skill.

Mobile-friendly is binding on every implementation node, not a later polish pass — owners open these previews on a phone. Every node below carries an explicit mobile step and a mobile completion test.

Submission format

Nested per page, written as question description : answer description. Numbers do not appear at all — the operator reads the submission directly rather than decoding it. One answer per line, so a question or option containing a comma cannot corrupt the structure.

Ridgeline Motorworks
build: 20260806-142209-a3f9c1
{
  home {
    Body text size: Increase by 25%
    Heading size: Keep as-is
    Main photo: Replace — I will send a new one
    Photo size: Increase by 25%
    Call-to-action button: Make larger by 25%
    Anything else: "the hero photo is the old unit"
  }
  services {
    Body text size: Keep as-is
    Number of services shown: Reduce to 4
    Service card layout: Switch to two columns
    Section order: Move above Gallery
    Anything else: "we no longer do bodywork"
  }
  reviews { No Action }
  about   { No Action }
}
Why this is better than numbers. A numbered body is only meaningful against the exact config version that produced it — re-word an option six weeks later and every archived submission silently changes meaning. Descriptive text is self-contained: it stays correct no matter how the config evolves, and it needs no decoder to be actioned.
The cost is body length. Descriptive text is far longer than 1:2. A 13-screen site at 5 questions per screen runs to roughly 4KB before free text, and some mobile mail clients truncate a mailto: body well below that. This is now the single highest delivery risk in the workflow — see submit (3.3), where it must be measured at full site size rather than on a sample.

Concrete schemas

Pinned down so an implementer is not choosing field names mid-build.

transform operation shape

{
  type: "transform",
  text: "Increase by 25%",
  operation: {
    property: "bodyTextSize",
    action: "increase",
    magnitude: 0.25,
    unit: "relative"
  }
}

For options with no meaningful magnitude ("Switch to two columns", "Move above Gallery"), action is the operation and magnitude/unit are omitted rather than left as null — a present-but-empty field invites a build step to check for null and forget to; an absent field cannot be forgotten in the same way.

ownerReviewBuildId format

YYYYMMDD-HHmmss-<6-char-hash>, e.g. 20260806-142209-a3f9c1. Timestamp of the generation run plus a short hash of the build inputs, so two builds seconds apart are still distinguishable even if the hash portion alone were to collide.

ownerReviewStorageKey derivation

owner_review::<business_slug>, e.g. owner_review::ridgeline-motorworks. The business slug is whatever already uniquely identifies the business elsewhere in the generated config — reused, not newly invented, so two systems can never disagree about a business's identity.

Submission subject line

Fixed template: Website review — <business name>. Never includes the build id or a screen count — those live in the body, where the automated parser reads them; the subject exists for a human scanning an inbox, and stays stable so submissions from the same business thread visually together.

Discrete options — the interpretation rule

Every option must be applicable without asking the owner a follow-up question. That is the test. Increase font by 25% passes — it names the property, the direction and the magnitude. Small tweak needed fails — it says something is wrong but not what to do, so it cannot be applied by anyone without going back to the owner.

The five options currently shipped in owner-review-config.js — Keep as-is, Small tweak needed, Significant change needed, Not sure let's discuss, Remove this section — are four failures and one pass. Only "Keep as-is" and "Remove this section" are exact. The rest record dissatisfaction without recording an instruction, which is precisely the ambiguity the skill was written to eliminate.

This forces two structural changes

  • Options become per-question, not one shared global list. A single flat ownerReviewOptions array cannot be discrete — "Increase by 25%" is meaningful for a font-size question and meaningless for a photo-choice question. Each question must carry its own option set.
  • Questions become properties, not topics. "Overall design and layout" is too broad to have exact answers. It splits into the specific adjustable properties beneath it — body text size, heading size, photo size, section order, button size — each with its own discrete option set.

Option types

Each option declares a type. At prospect stage there is no human backstop, so a type is only viable if it either applies by machine or has a defined destination that survives until activation.

  • none — "Keep as-is". The null action. Always the first option.
  • transform — "Increase by 25%", "Reduce to 4", "Switch to two columns". Exact, machine-applicable, and carries its operation in config. Applied directly.
  • asset — "Replace this photo", "Add my logo". Exact as an instruction, but cannot complete while upload is scrapped. Routed to the LLM lane for chasing rather than applied. Revisit if upload returns.
  • escalate — dead. It meant "a human will pick this up right now", and at prospect stage no one will. Post-activation handling is covered by the free-text and loose-asset routes, which do not need an option type of their own.
Vague options are worse than vague free text, because they masquerade as structured data — an automated interpreter will treat "Small tweak needed" as a legitimate answer and have no defined operation to apply. Free text at least announces its own ambiguity. What happens to that free text with no human to read it is an open decision, below.

Automated interpretation — safety requirements

No human checks a prospect's review. Before payment the submission acts on the generated site with nobody in the path — no triage, no approval, no backstop. A parser that guesses at an unrecognised line applies the wrong change and nobody notices until the owner does. Exactness is a safety property here, not a preference, and every "flag it for review" escape hatch is unavailable.
Human review becomes available once the client is paying. This is an economic boundary, not a technical one: unpaid prospects arrive at whatever volume the outreach generates, so their reviews must be actioned automatically or not at all. A paying client is a bounded, funded population who can be given real attention. Everything in this lane — discrete options, fail-closed parsing, no free-text interpretation — is a prospect-stage constraint that relaxes after activation.
The practical consequence: anything a prospect asks for that automation cannot apply exactly is not lost — it is recorded against their review and becomes actionable by a human once they activate. That gives the free-text field a real destination without ever letting an automated interpreter guess at it.

Consequences that follow

  • The submission must carry its build id. Interpretation resolves each answer against the exact config that produced the site, not whatever the config says today. Without it, re-wording an option silently changes how every in-flight submission is interpreted. The buildId already exists in the store for staleness detection and must now travel with the email too.
  • Options carry the operation, not just the words. A transform option declares its machine-readable effect in config — property, action, magnitude — so automation applies a defined operation rather than parsing English. The descriptive text in the email is the readable rendering of that operation, never the source of truth for it.
  • Option text must be unique within its question. Text is the join key between email and config, so two options in one question sharing a label makes the mapping ambiguous. This must fail at build time, not at interpretation time.
  • Fail closed on any unmatched line — apply nothing. With no human to escalate to, the only safe response to a line that cannot be matched exactly is to abandon the whole submission and change nothing. A partially applied review is worse than an unapplied one: the owner sees some of their requests honoured and cannot tell which were dropped. Never fuzzy-match, never pick the nearest option, never silently skip a line.
  • Failure must notify the owner automatically. Fail-closed is only safe if somebody learns about it, and the only party available is the owner. A submission that could not be applied triggers an automated message saying so — otherwise it fails into silence and they wait indefinitely for changes that will never come.
  • Round-trip determinism is a release gate. Compose → parse must recover the exact operation for every option in the config, verified across the whole option set rather than a sample, before automated regeneration is permitted to act on any submission at all.

Free text — assessed by an LLM as a separate lane

"Anything else" is read by an LLM, which determines a separate action rather than producing a change. This is a parallel lane, not part of the deterministic pipeline — and the distinction is the entire safety argument.

Why this does not undermine the discreteness rule. The LLM never emits a transform and never edits the site. Discrete options continue down the exact, config-resolved path untouched. The LLM's only output is a decision about what should happen with that note — which is a judgement call that no amount of exactness elsewhere was ever going to cover.

Uploads — scrapped for now

No upload control in the panel. The review captures answers only, and any file an owner needs to supply is chased separately.

This deferral resolves both conflicts the upload path created. With no file to place, the review layer stays genuinely static — no hosted destination, no posting endpoint, no exception to the skill's founding rule. And pause-and-resume works cleanly again, because every answer remains a few bytes in localStorage rather than a file that cannot live there.
asset options cannot complete without an upload. "Replace this photo" is still a legitimate thing for an owner to say, but with nowhere to attach the file it is an instruction with nothing behind it. Such answers resolve to the same separate-action lane as free text rather than to a transform — the LLM assesses what needs chasing. Revisit if and when upload returns.

The No Action rule — and the bug it fixes

Current shipped behaviour is wrong. owner-review-embed.js pre-checks option 1 on every radio and only emits a no-action marker when the owner ticks a checkbox. An untouched screen therefore submits 1:1, 2:1, 3:1, 4:1, 5:1 — byte-identical to a screen the owner deliberately marked "keep as-is" five times. The skill's own non-negotiable section requires these two to be distinguishable.
  • Absence is the signal. A screen is No Action because nothing was ever written for it, not because a default was submitted on the owner's behalf.
  • No pre-selected answers. Options start unselected. An answer exists only where the owner actually chose one.
  • Explicit happy path stays available. An owner who opens a screen and is content marks it reviewed-and-fine, which is recorded as real answers — distinct from silence.
  • Partial screens are honest. A screen with some questions answered emits only those, rather than padding the rest with option 1.

Storage contract

  • Key: one localStorage entry per business, namespaced so two previews on the same host cannot collide.
  • Shape (in progress): 
    {
  buildId: "20260806-142209-a3f9c1",
  lastUpdatedAt: "2026-08-06T14:30:02.000Z",
  lastScreen: "gallery",
  submittedBuildId: null,
  submittedAt: null,
  screens: {
    home: {
      answers: { 1: 2, 3: 1 },
      freeText: "the hero photo is the old unit",
      firstOpenedAt: "2026-08-06T14:22:10.000Z"
    }
  }
}
    A screen key exists only once the owner has interacted with it. Answer keys are question numbers (1-indexed, matching config order); missing keys mean that question was left unanswered on a partially reviewed screen.
  • Shape (after confirmed submit): screens is cleared to {}, but submittedBuildId and submittedAt are set and survive the clear — this is the entire mechanism behind the already-submitted state at owner (2.6b).
  • Indices internally, text at the boundary. The store keeps answers as question and option indices; the descriptive text is resolved from config only when the submission is composed. Storing indices keeps the entry small and lets option wording be corrected mid-review without rewriting stored state — and buildId guards the case where the wording changed enough to make a paused review stale.
  • No files, by design. With upload scrapped the store holds only small values, which is what keeps pause-and-resume reliable — localStorage quota is roughly 5MB total and base64 inflates by a third, so a photo could never have lived here safely anyway.
  • Written on change, not on a save button — an owner who wanders off mid-review loses nothing.
  • Resume fields. lastUpdatedAt and lastScreen drive the resume prompt; buildId lets a regenerated site detect that an in-progress review belongs to an earlier version rather than silently applying stale answers.
  • No expiry. A paused review is not timed out. It clears on successful submit, on explicit discard, or when the owner clears their browser — nothing else.
  • Cleared after a successful submit so a later revision round starts clean against the regenerated site.
  • Accepted cost: a cleared browser or a different device loses an in-progress review, including a paused one. The skill's no-backend rule leaves no alternative on a static site — a review that survives a device change would require server-side state, which is an EP047 concern, not this layer.

Resolving "which screen am I on"

Generated sites come in both shapes, so the resolver must handle both without per-site code.

  • Multi-page sites (e.g. Test02, 13 separate .html files): screen resolved from the current path against each screen's declared route.
  • Single-page sites (the auto-garage-template reference, whose screens are anchor sections such as #services): screen resolved from whichever section is currently in view.
  • Fallback: if neither resolves, the launcher's label is replaced by a "Which page is this?" picker populated from ownerReviewScreens, defaulting to no selection. Once chosen, the panel opens for that screen exactly as if resolution had succeeded — a one-time disambiguation, not a persistent mode, and rare in practice since it only triggers outside the two known site shapes.

Mobile requirements — binding on every implementation node

Phone is the primary review device. The preview link arrives by email and is most often opened on a phone, so a review layer that only works comfortably on desktop fails at the exact moment it matters. No node is complete on desktop evidence alone.
  • Reference viewport 375 x 812. Every node's completion test must be executed at this size in addition to desktop, with device emulation on so touch behaviour applies rather than hover.
  • Touch targets minimum 44 x 44px for every option, launcher, amend control and submit button. Radio options are the highest risk — five stacked options per question is a lot of small targets if sized for a mouse.
  • The panel is a bottom sheet on mobile, not a centred desktop modal — it must open within thumb reach and be dismissible by swipe-down and by the hardware back gesture, not only by an X in a far corner.
  • The on-screen keyboard must never obscure the free-text field. The field must scroll into view on focus and stay visible while typing.
  • No horizontal scroll anywhere. Long option text wraps; the consolidation summary is a stacked card list on mobile, never a table.
  • Respect safe-area insets so the launcher and submit button clear the home indicator and any notch.
  • No collision with the site's own sticky elements — the existing sticky call-to-action bar and mobile menu already occupy the bottom of the viewport on generated sites.
  • Section resolution must be tuned for short viewports. IntersectionObserver thresholds calibrated on a desktop viewport will resolve the wrong screen on a phone, where far less of any section is visible at once.
  • iOS private mode throws on localStorage write. The store's degrade-to-memory path must be verified on mobile Safari specifically, not assumed from desktop behaviour.

Unchanged rules inherited from the skill

  • No backend, no database, no API call — the review layer stays entirely static.
  • No live tracking beacon. Timestamps are client-side and travel with the submission; the operator learns nothing until the owner submits, so reminder nudges key off absence of a submission.
  • Submission goes to the operator's inbox, never the business's own customer-facing address.
  • Flag-toggled (OWNER_REVIEW_ENABLED), same self-contained pattern as assistant-embed.js.
  • Category skills tailor question and option wording; the questions x options x free-text x no-action shape is fixed.

What a category skill must now concretely produce

Not just "harder" — a specific, checkable deliverable per trade, replacing the single generic severity scale every category previously shared:

  • A list of adjustable properties for that trade's site, not topics — e.g. a plumbing site might adjust "emergency callout banner visibility" where a garage site adjusts "MOT reminder placement." Properties come from what a category skill author knows actually varies for that trade, not a copy of the generic five.
  • 2–5 discrete options per property, each passing the interpretation test unaided — every option authored must be checked against "can this be applied without a follow-up question?" before it ships, the same audit gate build (1.1) enforces mechanically for uniqueness but cannot enforce for exactness.
  • An operation for every transform option in the fixed shape above — a category skill that writes exact-sounding option text but skips the operation object still fails the build, since the operation is what automation actually runs.
  • No new option types. Only none, transform and asset exist; a category skill cannot invent a fourth type to route around the discreteness rule for something that is genuinely subjective — that case belongs in the free-text lane, not a new option type.
One skill rule is superseded and must be rewritten. The skill currently states "Owner never sees numbers — only the real option text. Numbers are in the email body for parsing." Numbers no longer appear in the body at all. The first half still holds; the second is now wrong and is a required edit in the skill rewrite.
