Public News date and display rules

EP047 proposed configuration feature — determine one effective story date from source evidence, then use it for public ordering and bounded town views. This document describes the target behavior only; the current public API still returns all eligible published stories.

Proposed date provenance and effective-date route

Research

Seek original event date

Research should look for the date the event or news actually happened, not just the date a page was found.

→
Date hierarchy

Choose reliable date

Use original event date when reliable; otherwise source publication date; otherwise our database publication timestamp.

→
Provenance

Store date evidence

Store the chosen date, date type, source URL, extraction note and confidence so the decision can be audited.

→
Display field

Set effective story date

Determine one effective date used consistently for recency, ordering, labels and history-window calculations.

→
Deduplication

Match before draft

Normalize canonical source URL, headline, town, effective date and event identity before a record can enter draft or publication.

→
Public order

Newest effective-date first

Town pages show the newest eligible stories by effective date, with a stable secondary order for ties.

→
Public dedupe

Collapse duplicate events

Public display collapses duplicate records so one event is not shown twice, while retaining the underlying audit history.

Public town display and history

Eligibility

Keep published + visible

Published status and existing town/category/business visibility eligibility still apply before display limits.

→
Default view

Bounded recent stories

Show stories within the configured lookback window and stop at the configured per-town maximum.

→

A history link lets readers browse the configured recent period without overloading the default town page.

Retention

Current implementation boundary — not yet this feature

Current API

All eligible published stories

The current public API returns all eligible published stories and has no date window or article limit.

→
Missing field

No dedicated source/event date

The current schema/API lacks a dedicated original event date or source publication date field; this workflow proposes adding that capability.

Failure, fallback and safety rules

Fallback

Use next reliable date

If original event date is not reliable, fall back to source publication date, then database publication timestamp, with provenance recorded.

→
Duplicate review

Hold likely matches

Reject or hold same-source duplicates and likely cross-source duplicates for review; record the matching fields and why the story was matched.

→
Published safety

Never silently overwrite

A duplicate match never silently replaces a published story. Preserve both records and the decision/audit trail.

→
Failure

Do not silently publish

Missing or contradictory date evidence stays flagged for review; do not invent a date or expose an unsafe ordering.

→
Scope safety

Preserve visibility rules

Date and limit settings never bypass published status or the existing public town/category/business eligibility resolver.
